# Folio ↔ FolioImageWorker: API v1

Воркер работает на ПК и **сам** обращается к публичному HTTPS-адресу Folio. Folio никогда не подключается к адресу ПК. Подключение к Folio и AI Tunnel выполняется напрямую, без VPN и прокси. Полную ссылку для `FOLIO_POLL_URL` показывает Folio → Настройки → Воркер изображений. Все запросы воркера содержат `Authorization: Bearer <WORKER_API_KEY>`; этот же ключ задаётся в Folio.

## 1. Получение задания

`GET https://<folio>/folio/image-worker/next`

- `204 No Content`: очередь пуста.
- `200 OK`: одно задание. До подтверждения результата повторный запрос возвращает то же задание и тот же `worker_id`. Воркер хранит `worker_id` и `folio_job_id` в SQLite, чтобы после перезапуска не запускать генерацию повторно.
- `401`: неправильный ключ.

```json
{
  "id": 123,
  "worker_id": "924539a0-d73e-4d62-a16d-2d35ce91a2cf",
  "prompt": "Заменить фон",
  "model": "seedream-5-0-lite",
  "width_cm": 40,
  "height_cm": 60,
  "image_urls": [
    "https://one.customcraft-mes.ru/folio/image-worker/input/<token>/0"
  ]
}
```

`image_urls` содержит 1–8 изображений в порядке брифа. Folio выдаёт ссылки со случайным токеном; отдельная авторизация для скачивания фото не нужна. Воркер скачивает и проверяет изображения, затем передаёт их локальные копии AI Tunnel в `input_references` как `data:image/png;base64,...`. Внешнему провайдеру не требуется скачивать изображения с Folio; ссылки с токенами ему не передаются.

`model` фиксируется при постановке задания в очередь. Бюджетные профили: `seedream-5-0-lite` (4K), `seedream-4.5` (4K), `seedream-5-0-flash` (2K), `hy-image-v3.5-preview` (4K). Все принимают до 8 исходников Folio. Если поля нет в старом задании, используется HY Image. Старые `flux-3-image`, `gemini-nano-banana-2.1`, `seedream-5-0-pro` распознаются для совместимости, но новая платная генерация блокируется: модели не укладываются в выбранный бюджет. Существующий готовый файл можно использовать без повторной генерации. Воркер сообщает поддержку выбора модели заголовком `X-Folio-Image-Models: 1` и провайдер заголовком `X-Folio-Image-Provider: aitunnel` (или `mock`). Перед выбором новых моделей необходимо обновить воркер; общий флаг версии 1 сам по себе не подтверждает поддержку новых названий старым воркером.

## 2. Состояние и результат

### Подготовка промпта (13.10.2026)

Задание может содержать `prompt_mode`: `direct` (старое поведение, значение для
заданий без поля) или `vision`. Core фиксирует режим при постановке в очередь,
из настройки UI «Подготовка промпта». Старые задания не мигрируются.
Воркер объявляет `X-Folio-Prompt-Planner: 1`; Core не выдаёт vision-задание старому
воркеру. Vision поддерживается в pull-подключении с AI Tunnel.

В режиме vision Gemini 2.5 Flash Lite получает исходные фото, инструкцию и размер
через `/chat/completions`. Итоговая инструкция до 3500 символов сохраняется в
`prompt-plan.json` с отпечатком входных данных и фактической стоимостью.
Системная инструкция LLM восстановлена из исходного сравнительного теста и
дополнена сохранением позы, поворота головы и ракурса. Генератор получает исходные
фото и ответ LLM без дополнительного длинного блока ограничений.
Промпты и изображения не выводятся в журналы. Используется существующий ключ AI Tunnel.
После потери ответа LLM или перезапуска с отметкой запроса без результата — unknown,
без автоматической повторной оплаты. Ошибка/обрезанный ответ LLM не запускает
генерацию. При наличии сохранённого результата LLM повторно не вызывается.
Новый режим не меняет превью, печатные поля, Topaz и доставку результата.


`POST https://<folio>/folio/image-worker/jobs/{id}` с `multipart/form-data` и тем же Bearer-ключом:

| Поле | Значение |
| --- | --- |
| `worker_id` | UUID из задания |
| `status` | `queued`, `generating`, `waiting_topaz`, `composing`, `completed`, `failed` или `unknown` (результат платного запроса не подтверждён) |
| `print_file` | Полный UNC или локальный путь к TIFF, обязателен при `completed` |
| `error` | Короткая причина ошибки при `failed` или `unknown` |
| `preview` | JPEG-файл, обязателен при `completed`; наибольшая сторона ровно 1000 px, до 10 МиБ |

Успешный ответ: `200 {"ok":true}`. Повторение того же завершённого результата безопасно. Folio сохраняет JPEG в своём хранилище и даёт блоку сценария **«Отправить макет»** отправить его покупателю через Ozon. При ошибке сценарий идёт по ветке ошибки блока создания макета.

Очередь выполняет одно задание за раз. Воркер повторяет запрос к Folio каждые несколько секунд, а отправку статуса после временной сетевой ошибки повторяет до подтверждения. Счётчик и время следующей попытки доставки хранятся отдельно для каждого задания, поэтому сбой одного результата не блокирует остальные. Ответы `409 image_worker_result_conflict` и `404 image_worker_job_unknown` останавливают доставку только устаревшего состояния этого задания; ошибка остаётся в БД и журнале, успешная доставка не имитируется. Folio не опрашивает воркер.

## Обработка и файлы

Для новых заданий `IMAGE_PROVIDER=aitunnel` воркер вызывает `POST /v1/images/generations` на основном или резервном официальном хосте AI Tunnel с зафиксированной моделью задания, 1–8 референсами, инструкцией, поддерживаемым для модели разрешением и ближайшим соотношением сторон. AI Tunnel возвращает готовое изображение синхронно в `data[0].b64_json`; опроса внешней задачи и callback нет. Старые задания Nano Banana сохраняют свой провайдер в SQLite и завершаются по прежнему API.

Перед платным запросом воркер сохраняет в SQLite отметку о начале отправки. При ошибке подключения до отправки запроса он переключается с `api.aitunnel.ru` на `ru-api.aitunnel.ru`. По заданному для этой интеграции правилу HTTP 504 не списывает оплату: воркер повторяет запрос до трёх попыток, переключаясь на зеркало после первой. После трёх ответов 504 задание завершается ошибкой. Если получен другой HTTP 5xx, ответ потерян или процесс перезапущен до сохранения изображения, статус становится `unknown`: воркер **не повторяет** платный POST автоматически, а Folio не продолжает сценарий. Результат и возможное списание следует проверить вручную. Баланс аккаунта и кэшируемая статистика ключа не связывают расход с конкретным заданием, поэтому не служат разрешением на повтор. Без `AITUNNEL_API_KEY` в режиме `aitunnel` новые задания из Folio не забираются. Превью, Topaz и печатный TIFF собираются локально после получения результата, как и прежде.

После генерации воркер сравнивает длинные стороны исходного изображения и видимой части макета в пикселях. Если макет длиннее на **3000 px или больше**, Windows-агент запускает Topaz; иначе макет собирается сразу из результата генерации. `width_cm` и `height_cm` задают **видимую часть картины**, а не размер всего печатного листа. Её размер в пикселях — `round(cm / 2.54 × 150)` по каждой стороне. Превью показывает только эту часть и не меняется из-за полей.

Печатный TIFF содержит видимую часть, затем зеркальное продолжение изображения со всех четырёх сторон, затем белое поле со всех четырёх сторон. Ширина каждого поля зависит от большей стороны видимой части:

| Большая сторона | Зеркало с каждой стороны | Белое поле с каждой стороны |
| --- | ---: | ---: |
| До 60 см включительно | 2,5 см | 3,5 см |
| Свыше 60 до 90 см включительно | 4,5 см | 5 см |
| Свыше 90 см | 4,5 см | 7 см |

Например, для видимой части 40×60 см зеркало даёт 45×65 см, а TIFF с белыми полями — **52×72 см**. Общий размер TIFF вычисляется как `round((видимая сторона + 2 × (зеркало + белое поле)) / 2.54 × 150)` пикселей; из-за округления поля с противоположных сторон могут различаться на один пиксель. Метаданные TIFF остаются 150 DPI. Агент копирует его в `PRINT_SHARE_PATH` через доступ Windows к UNC-папке. Если UNC пока нет, TIFF остаётся локально в `spool/<worker_id>/print.tif`.

`GET /health` и `POST /v1/jobs` остались внутри контейнера для диагностики и ручных тестов. Порт 8000 не опубликован на ПК: Folio его не вызывает.
